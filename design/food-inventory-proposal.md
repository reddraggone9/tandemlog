# Food inventory: proposal for review

Status: planning only. No food implementation or private source records. Persistence migration remains the primary implementation work. Confirmed requirements are separated below from proposed UX/semantics.

## Confirmed behavior and import

Ordinary dated stock is one globally expiration-ordered list by default. Only retained-reason groups mirror the existing initially collapsed behavior. A retention reason hides an entry from the ordinary list even before expiry. Assigning a reason and filtering reasons use the shared task-tag-style autocomplete; there is no assignee field. Search matches all terms, ignores normal reason filters, and surfaces retained active stock. Undated entries stay visible in a needs-expiration inbox until a known or estimated date is supplied.

Deleted is durable, newest deletion first, without an age cutoff. Restore works across days/restarts; session Undo complements it. Active search excludes deleted stock; explicit Deleted search never restores matching results. No consumed/discarded distinction is needed initially. Nutrition automation remains future work, but manual partial-container representation is now in scope.

Lee confirmed that `xN`/`x N` means whole-container count and an absent suffix means one; source names have been normalized toward `x N`. The private contract is approved: 399 active entries expand to 448 physical containers; 126 clear brand labels cover 352 notes. Twenty-four uncertain, five brand-only and eighteen unmatched names retain their name and unset brand, except for the confirmed count suffix. Brand is a separate field. Initial import extracts only confirmed counts and that explicit brand whitelist. It does not extract size, units or remaining-content text; those stay in the names until Lee edits them manually after import. No brand is inferred outside the approved whitelist. The exact source/whitelist contract stays outside this repository; no user count/brand decision remains pending.

Import all nondeleted source entries; exclude deleted notes and physical trash. Preserve source IDs, creation times, calendar expiration (including the existing datetime case) and retention. Do not merge source identity by name. Legacy estimated-versus-known expiration remains unknown unless evidence supplies it. Before cutover, freeze source editing, snapshot, reconcile source fields and container counts, and verify an idempotent source-ID/container-ordinal mapping. Keep original names in private staging. No size/unit normalization artifacts are required for initial import.

## Proposed model and grouping

Use one stable identity per physical container. Expand each imported source entry's confirmed count into stable container identities; preserve source-entry identity plus container ordinal so repeated import creates no duplicates. New stock creates fresh container IDs. Keep display name, optional brand, created time, exact calendar expiration, estimate status, retention reason, optional location and deletion state. Nominal size is optional and manually editable after import.

Identical descriptive data and identical expiration can collapse into one visible row. Grouping is a projection, never a replacement of container identities. Different expirations always stay separate and participate in global expiration sorting. Proposed groups share name, brand, exact expiry, estimate status, retention reason, location and nominal size; each container retains its own remaining contents. Inspection exposes those containers when a user needs a precise target.

Represent remaining contents per container separately from physical count and nominal size: seven full one-pound bags plus one bag one-third full means eight physical containers and seven-and-one-third full-container equivalents. Store an explicit fraction/amount with its unit/nominal-size basis; do not reinterpret historical whole-container counts as mass. Keep unmeasured contents unknown instead of guessing. Imported remaining contents stay unspecified because the importer does not parse that text; names remain intact for manual correction. Newly added containers can default to full as an explicit new-entry proposal.

Lee tentatively accepted `7 full + ⅓ remaining` for a prototype. Use that concise summary in a compact grouped row, with inspection showing eight physical containers and each remaining amount. It is not frozen final wording; review actual narrow and wide layouts before adopting it. Imported unknown contents show the confirmed `x N` count until manually set. Seven full containers and one third-full container remain eight physical containers; a fractional contents summary never silently becomes a physical count.

## Proposed controls and deterministic behavior

Add creates the requested number of fresh container IDs. Remove on a grouped row names the quantity and target: whole-container removal selects actual observed IDs, with the full/partial composition visible before committing. Proposed default chooses full containers first, with inspection allowing a particular partial container to be selected. Manual contents edits target a specific container; they do not silently distribute a decrease over unrelated stock.

Delete on a grouped row captures the observed container IDs and clearly states how many full/partial containers will disappear. Concurrently added containers remain visible. Two offline removals of the same container remove that identity once; independent removals of different identities both count. Restore targets observed deletions and preserves container IDs and remaining contents. An unseen concurrent deletion stays deleted until reviewed/restored, preventing accidental stock resurrection. Test deterministic behavior and surface visible conflicts; Lee need not design merge algorithms.

Proposed Duplicate creates fresh container IDs, copies the reviewed descriptive data/expiry/remaining contents, and clears retention/deletion state. Confirm that UX before implementation. Remaining visible decisions are grouping density/inspection, partial-stock wording, and grouped removal/restore targeting. Food gets a separate canonical namespace and preserves all released task records. Product catalogs, recipes, receipt parsing, unit conversion and automated nutrition deductions remain deferred.
