# Android reconciliation and incremental checkpoints

Status: accepted by Lee and implemented for RC10 build37, 2026-10-03; exact native Android acceptance is pending. Canonical protocol remains v2.

## Approved normal-operation policy

Opening, resuming, polling and commands reuse persisted cache checkpoints. They do **not** schedule a hidden full historical audit. Directory notifications prompt debounced foreground reconciliation; a 15-second foreground fallback lists current documents when notifications are unavailable or coalesced. Suspension stops the watcher/timer and resume reconciles immediately. No background service or broad storage permission is added.

For adapters exposing current size and a genuine seek-based suffix read, unchanged complete logs read zero log bytes. Growth reads from the cached complete offset and validates only the new complete records. Fresh documents/descriptors are resolved for each read, including atomic replacement. Unknown size or a nonseekable descriptor returns an honest unsupported-range result and falls back to a full verified read; skipping through a pipe is not described as zero historical I/O. Provider observations detect likely changes; they are not content-integrity proof.

Cache 11 keeps the previously observed whole-prefix digest and its byte endpoint, then appends SHA256 hashes of exact newly admitted complete byte ranges. Events (literal admitted lines), affected projections and checkpoints commit in one SQLite transaction. There is no canonical hash chain, no serialized library SHA state and no rewriting of event clocks. A v10 cache gains range columns/table transactionally without historical reads; supported older projection caches rebuild with existing integrity/backup guards.

Manifest identity replacement, missing known logs, size truncation, conflict copies, invalid complete new records, invalid sequence/clock/references and incomplete owned tails fail visibly. Remote incomplete suffixes wait without advancing the complete checkpoint. Exact prepared event receipts remain necessary before command success. Unchanged scans do not rewrite identical checkpoints or revalidate every unrelated cached reference.

**Accepted tradeoff:** a same-length historical mutation, or a rewritten old prefix followed by valid growth, can remain invisible to the cached view until an explicit full check. An offset/range digest records what was observed; it does not prove those current bytes still exist. Lee chose this over rereading/rehashing growing history on dozens of ordinary daily launches. `TaskStore.verifyHistory()` explicitly compares contiguous cached baseline/ranges against current bytes, then admits valid new records. No permanent manual-refresh control or periodic full audit is added. Fresh reconstruction reads current logs, but deleting the old cache also deletes its prior rollback/mutation baseline. Sync is not backup or authentication.

## Implemented notifications and provider limits

The stock external-storage provider derives from AOSP `FileSystemProvider`. Its child-directory cursor starts a native directory watch and closes it when the last cursor closes. It sets a notification URI and reports create/delete/move/write changes through cursor/content notifications. The new adapter retains that child-directory cursor, registers on its supplied notification URI(s), requeries with the replacement watch installed before closing the old cursor, and closes resources on suspension, folder change and engine disposal. Merely observing an arbitrary tree URI without retaining the directory watch is insufficient. Observe the **directory**, re-resolve replaced children and never retain a file descriptor as evidence of the current pathname. [AOSP implementation](https://android.googlesource.com/platform/frameworks/base/+/988b22c44f51/core/java/com/android/internal/content/FileSystemProvider.java), [external-storage provider](https://android.googlesource.com/platform/frameworks/base/+/master/packages/ExternalStorageProvider/src/com/android/externalstorage/ExternalStorageProvider.java).

Other providers can behave differently. Query document ID, size and modification time together in one directory traversal, but treat missing values as uncertainty. Neither ID nor size/mtime is a cryptographic content generation. Providers may expose null timestamps/sizes; same-size replacement with retained metadata can evade those comparisons. SAF has no provider-independent trustworthy content-version column. Notifications are hints and cannot prove every event was delivered. [Document columns](https://developer.android.com/reference/android/provider/DocumentsContract.Document).

Read-mode descriptors can be pipes/socket pairs; seeking cannot be required of arbitrary SAF providers. A seekable descriptor can help read a suffix, but cannot prove its old prefix survived an atomic replacement. Syncthing transports an update through a temporary file and replaces the destination; our tree capability permits reopening the new document, not trusting the old handle. [Descriptor semantics](https://developer.android.com/reference/android/content/ContentResolver#openFileDescriptor(android.net.Uri,%20java.lang.String)), [Syncthing temporary files](https://docs.syncthing.net/users/syncing.html#temporary-files). Syncthing's direct filesystem access differs from our provider-independent SAF capabilities; its metadata scan strategy is not a proof that all SAF metadata is reliable.


## Measurements and verification

The earlier conservative adapter queried names, closed the cursor and supplied no size/notification support, so every 15-second Android-style refresh reread complete streams. A Linux synthetic production-store simulation with one 4,424,982-byte log took 120–124ms and read the entire log on an unchanged no-stamp pass; one edit read 8,850,221bytes in252ms. A separate SQLite probe confirmed unchanged checkpoint writes. These are the superseded algorithm's Linux Dart JIT costs, not Android/provider timings. The former suggestion to full-audit open/resume/every five minutes is superseded by Lee's accepted persisted-checkpoint policy.

A new separate-OS-process Linux production-store probe reopens exact 10,240-byte and1,048,576-byte histories with zero log bytes/read calls, taking61.103ms and60.334ms inside `TaskStore.open`. Twelve unchanged refreshes total10.757ms/12.260ms with zero log bytes. Subsequent growth reads exactly220/224suffix bytes at offsets10,240/1,048,576 and zero full-history bytes. Single samples, real filesystem seeks/SQLite, warm OS filesystem and package caches; the open timer excludes process launch/JIT and is not first-frame/input-ready cold-start timing or SAF performance. [Raw metrics and methodology](../evidence/rc10-incremental-history.json).

167 focused storage/adapter/importer tests pass, including fresh-cache reopen, append/partial tail, replacement/old-prefix blind spot, explicit audit, missing/truncated logs, cached coverage, unsupported ranges, schema migration, failure rollback and exact raw receipts. Kotlin compilation and adapter tests pass. Native Linux Inbox/profile/Filter cases pass; final aggregate and hosted candidate receipts are recorded in status/runtime QA.
