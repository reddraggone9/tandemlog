# Food import contract v1

Status: authorized bounded app-side interface; implemented with synthetic gates, independent review in progress. This is not approval to import live data. Private source extraction, brand whitelist, raw source, staging and provenance receipts stay outside Git. Only synthetic examples belong here.

Prepare one immutable reviewed JSON plan with exactly `v` (integer 1), `space` (selected canonical workspace UUID), `importId` (fresh canonical UUID generated once), `sourceSha256` (64 lowercase hex characters hashing the exact private source bytes), and `containers` (1–1000 physical containers). The UTF-8 plan limit is 4 MiB. Each container has exactly `sourceId` (opaque original identity, 1–512 UTF-8 bytes), `ordinal` (1–100000), `details`, `contents`, and `createdAt` (valid ISO timestamp with explicit Z/offset, at most 40 characters). Repeated source records use separate physical ordinals. Source ID plus ordinal must be unique. Do not substitute a historical sample count for the freshly reviewed source count.

`details` has exactly `name`, `brand`, `expiry`, `estimated`, `retention`, `location`, `size`, using existing Food validation. Preserve the reviewed normalized name/brand and original retention. `expiry` is the original calendar date YYYY-MM-DD or null; do not timezone-shift it. Unknown expiry certainty is `estimated:null`. `contents` has exactly `numerator`, `denominator`, `unit`: exact fractions/amounts canonicalize by GCD; unknown is all three null, never silently Full. Preserve original `createdAt` spelling and instant. If the source lacks it, preparation must explicitly record a reviewed fallback and retain that decision privately; the app does not invent it.

A physical target UUID is UUID-v5 with namespace `importId` and UTF-8 name `tandemlog:food-import:v1:` followed by canonical JSON `[sourceId,ordinal]`. Canonical JSON uses the existing recursive sorted-key encoder; array order is significant. Plan hash is SHA256 of UTF-8 `tandemlog:food-import-plan:v1\n` followed by canonical plan JSON (the domain ends with one literal newline). The source hash binds external bytes; the app cannot independently verify those unavailable bytes. Source extraction/provenance remains external. The writer is always the current admitted Food module writer derived from the protected settings installation UUID (the import API checks this binding); source IDs never select or impersonate a writer. Normal current clocks/sequences/hashes are authored by FoodStore. Import is ordinary Add history with fresh target IDs, not forged historical events.

Call `FoodStore.dryRunImport(plan)` to validate against the current owner/workspace/history and inspect targets, plan hash, writer and status. It never stages an import or appends Food records. Normal refresh may admit existing receipts/update derived state. `commitImport(plan)` is the separate explicit commit; it revalidates rather than trusting an earlier dry run. It uses the owner queue, guard, exact protected Food intents and canonical append path. No external adapter writes canonical files directly.

A dedicated protected per-space initialization row survives metadata ledger loss; a private complete index witnesses every immutable attempt ledger. The index and ledger bind namespace, source hash, plan hash and original record IDs/hashes, atomically with the initialization witness, guard reservation and exact receipt staging. There are at most 100 retained attempts per space; no ledger is pruned automatically. A missing index with retained attempts or a retained initialization witness, a missing indexed attempt, or missing initialization witness with retained ledger rows fails closed. A matching source cannot acquire a second namespace within this local profile. A changed source, count, order or normalized plan after an attempt is refused: retain the original plan and namespace, and resolve it before preparing a separately approved import. Existing target IDs without a matching ledger are collisions, not permission to adopt or mint substitutes. Ledger/source binding loss or inconsistency fails closed when detectable from retained records/receipts/other attempt evidence. Loss of both all ledger metadata and the independent witness, even if other profile tables survive, cannot establish prior provenance for a fresh namespace; do not reset those authorities or infer permission to reimport. Private backup of the plan/provenance remains necessary; local-profile loss cannot establish global one-time import across unrelated installations. Choose one designated installation for this private operation.

If append throws, do not generate a new namespace or repeat ordinary Add. Keep the immutable plan and retry `commitImport(plan)` on the same installation/profile. Partial and ambiguous append resume only the original exact protected byte suffix, with the original IDs, clocks, sequences and hashes; no fresh reservation/reimport. Cold reopen may already admit a successful uncertain write. Once all originals are admitted, repeated commit returns Committed with the original record IDs and appends nothing, even after later user edits/deletion. Projection fields are not idempotency evidence. Unrelated pending commands are not recovered on behalf of this import. Transport/history failure leaves recovery pending; shared manifest/profile/guard/receipt failures remain hard, never converted to a Food-only error.

Staged rehearsal must show dry-run no append, explicit commit, partial/ambiguous restart recovery, cold canonical replay, exact repeat refusal/no-op, and unchanged Tasks/settings. Older task-only peers in separate profiles ignore ordinary `.foodlog`; task scalar v3 wire bytes and semantics remain unchanged. Older peers' global conflict handling can still stop on Food conflict copies; this interface does not retrofit their behavior. Local schema downgrade and simultaneous old/new use of one profile are unsupported. The import witness table is additive within unreleased local schema 3; released schema 1/2 definitions are preserved and upgrade transactionally. Early unreleased schema-3 profiles lacking it are rejected rather than silently recreated. No live import, data deletion, platform-native acceptance, or release acceptance is claimed by this contract.
