# Repository working rules

- Approved stack: Flutter/Dart + SQLite cache + canonical per-device JSON logs; provider-independent serverless folder sync. The one native bridge is the Rust Yrs text engine ([ADR0010](design/decisions/0010-collaborative-text-adoption.md)); add no other without concrete need. Tasks and Food are released modules.
- Read [design/README.md](design/README.md) first, then only the documents it names for the area you are changing; history lives in `design/archive/` and `evidence/` and is not required reading. User instructions override older documents. Distinguish accepted scope, proposed decisions, deferred ideas, and implemented behavior; never silently promote a proposal to a commitment.
- Keep product behavior in `design/product-behavior.md`, boundaries in `design/architecture.md`, persistence in `design/storage-and-sync.md`, and platform choices in `design/tech-stack.md`. Link instead of duplicating rules. Archive superseded rationale; keep the index current.
- Review product design alongside architecture at milestones and periodically during sustained work: check consistency with user goals, setup continuity, everyday information density, progressive disclosure, platform differences and accessibility. Capture the reason, tradeoffs and rejected alternatives for consequential UI choices; do not retain explanatory clutter merely because it already exists.
- Record consequential choices in `design/decisions/` with status, context, alternatives, consequences, and revisit trigger. Seek Lee's decision for substantive product/stack changes. Routine reversible research and maintenance do not require renewed approval.
- Keep domain rules independent of UI, file transport, database APIs, clocks, and model providers. Use explicit commands and adapters; do not introduce generic frameworks for hypothetical modules.
- Review the whole architecture at milestone completion, periodically during sustained development, and when a new feature crosses module boundaries. Look for small duplication, awkward abstractions, stale/unreachable data or code not caught by the compiler, docs drift and test gaps. Refactor recurring coupling before adding another workaround; explain scope and migration effects. Avoid unrelated rewrites.
- Compatibility boundary: the coordinated cutover in [ADR0031](design/decisions/0031-coordinated-unified-cutover.md) was carried out with stable 2026.10.7 (2026-10-27). The pre-cutover v3 wire readers were removed under Lee's explicit authorization for that one cutover; it is not a precedent. From 2026.10.7 onward every release reads all history written by earlier releases, with unchanged meaning. A format change ships in one release: an older install that meets newer records stops with the Update screen and writes nothing, and a feature is never split into a reader release and a writer release (Lee, 2026-10-27). Every persisted format/meaning change needs compatibility behavior, frozen historical fixtures, deterministic replay checks, and a recovery path. Do not regenerate accepted fixture bytes to make a new decoder pass, reinterpret old payloads/hashes/clocks/UUIDs/Undo, reset data, or rewrite canonical history as a cache migration.
- Test invariants, duplicate/reordered delivery, crash recovery, and realistic workflows. Run relevant checks; do not claim unrun checks or use browser coverage as native platform evidence.
- New or materially changed user actions must maintain the [performance coverage contract](design/performance-gate.md#maintaining-action-coverage): set intended responsiveness budgets before initial acceptance, register cases, correctness assertions and faithful UI-path coverage, with history-growth checks where relevant. Do not auto-baseline a slow first implementation; responsiveness in human time sets what is acceptable, and calibrated regression bounds keep fast actions from drifting (see [What sets acceptable latency](design/performance-gate.md#what-sets-acceptable-latency-lee-2026-10-27); "100 ms" is not a target). Spend optimization effort on idle/background work and history-growing per-action cost, not on already fast, flat actions. Necessary budget exceptions require Lee's informed approval. Review the actual UI/action inventory as well as CI; storage timings alone do not establish visible responsiveness. Only Lee may approve looser limits; retain the current one-sample automatic same-label confirmation rule.
- UX pass for every new or non-trivially changed screen, row or dialog (Lee 2026-11-02; goal: UI right the first time). BEFORE building, add a short UX brief to the feature's design doc: the question the screen answers for Lee/Hester, what each row/dialog shows and in what order, what's deliberately left out, which existing pattern it reuses, and the next action the user will want (open the item, Undo, a link). AFTER it runs natively, an independent reviewer subagent (not the builder) gets only screenshots (dark + light, wide + 390 px, 200% text), the brief and [design/ux-principles.md](design/ux-principles.md), and returns concrete problems. Fix clear findings before Lee sees anything; list judgment calls for him. Add a rule to ux-principles.md whenever Lee corrects a UI.
- For every UI creation/change, run and visually inspect the changed workflow. Record viewport/platform, screenshots, observations, and resulting redesign or open question. Test keyboard/touch, loading/empty/error states, and persistence as relevant. Blocked runtime checks remain explicitly pending.
- Send Lee review captures (screenshots or short videos) of UI changes as soon as they exist, before RC work (Lee, 2026-10-26): dark theme, real native build when possible, widget-test or synthetic captures labelled as such. Label the actual OS/device and build; a browser at phone width is not Android, and Linux desktop is not Windows. In videos make inputs visible (desktop pointer; Android Show taps when available). Follow `design/runtime-qa.md` for evidence and gaps.
- Track technical debt with impact, owner, exit condition, and revisit milestone. Update docs in the same change as behavior. Local changes and normal non-force pushes to main are authorized. Public experimental prereleases are authorized only after the full candidate gates pass; mark prerelease=true and latest=false. Lee's standing approval permits reviewed stable updates without user-facing behavior changes after all release gates; behavior-changing stable releases need his explicit acceptance. Paid runners, protection changes and new long-lived signing credentials require separate approval. See `design/releases.md`.
- Dependency automation proposes bounded PRs; never automatically merge. Review exact changed direct/transitive source, provenance, native payloads and install/build hooks before executing an update, then test actual application impact and affected native workflows. Prior version trust is not an audit of the next version. Keep the inventory and per-version review in `design/dependencies.md` current.
- Follow the end-user release-note editorial policy in `design/releases.md`: changes, fixes and improvements belong in release notes; expected behavior and QA/preservation assurances belong in evidence or private handoffs. Require a separate review of the actual notes, media and covered diff before publishing; use cropped real-app Before/After images where they help explain a visible change.
